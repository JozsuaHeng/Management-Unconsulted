# Government Tender / RFQ Response

## When to use this

A government agency or public-sector body has issued an RFQ/RFT and the
user needs a structured response — distinct from a general client
proposal (`proposal-sow-drafter`) because government responses are
evaluated against explicit, published criteria and require standard
compliance declarations.

## When NOT to use this

- A general private-sector client proposal with no formal evaluation
  criteria or compliance requirements — use `proposal-sow-drafter`,
  which is less rigid and more relationship-driven.
- The RFQ/RFT document and its evaluation criteria haven't actually been
  reviewed yet — read those first; this response should be built around
  them, not written generically and hoped to fit.

## Workflow

1. **Read the RFQ's evaluation criteria first**, before drafting
   anything — evaluators score against stated criteria, not against how
   good the response reads. Structure the whole response so each
   criterion is explicitly, visibly addressed (not just implicitly
   covered somewhere in the prose).
2. **State understanding of requirements in the buyer's own language**,
   referencing their actual stated objectives and context — a response
   that reads as generic/templated is an easy one for an evaluator to
   discount.
3. **Build a genuine value proposition tied to evidence** — track
   record, price competitiveness, specific sector experience relevant
   to this buyer — not generic claims ("we're the best," "outstanding
   value") with nothing backing them.
4. **Present the proposed approach concretely** — what will actually be
   done, in what sequence, producing what outputs — mirroring how the
   RFQ describes the need, so the evaluator can map response to
   requirement easily.
5. **State the commercial offer clearly** — rates, total cost estimate,
   any panel arrangement or existing pre-negotiated rate that applies.
6. **Address standard declarations explicitly** — conflict of interest
   (or lack thereof), compliance with any stated requirements — missing
   these can disqualify an otherwise strong response outright, so treat
   them as non-negotiable inclusions, not an afterthought.

## Output format

```
## Response: [RFQ/RFT name] — [issuing agency]

### Understanding of requirements
[In the buyer's language, referencing their stated context]

### Value proposition
[Specific, evidence-backed — not generic claims]

### Proposed approach
[Concrete steps/phases, mapped to what the RFQ actually asked for]

### Capability & experience
[Relevant track record — specific, not a generic capability statement]

### Commercial offer
[Rates / total cost / panel arrangement if relevant]

### Declarations
- Conflict of interest: [statement]
- [Any other standard compliance declarations required by this RFQ]

### Evaluation criteria cross-check
[Confirm each stated evaluation criterion is addressed somewhere above —
list criterion → where it's addressed]
```

## Common pitfalls

- Writing a strong general proposal that doesn't map explicitly to the
  RFQ's actual evaluation criteria — loses marks even when the content
  is good, because evaluators score against criteria, not impressions.
- Generic value propositions with no specific evidence attached.
- Missing a required declaration (conflict of interest, compliance
  statement) — can disqualify the response regardless of quality
  elsewhere.
- Templated language that doesn't reference the buyer's specific
  context, reading as copy-pasted from a previous response.

## Quality checklist

- [ ] Every stated evaluation criterion is explicitly addressed and
      cross-checked at the end
- [ ] Value proposition claims are backed by specific evidence
- [ ] Standard declarations are included, not omitted
- [ ] Language references the buyer's actual context, not generic
      boilerplate
