# Worked example: illustrative, generic internal tools replacement project

| Factor | This project's situation | Implication |
|---|---|---|
| Requirement stability | Core workflow is well understood, but the UI/UX approach is genuinely open | Mixed — leans hybrid |
| Stakeholder feedback need | High — end users have strong, varied opinions on workflow | Favours Agile for the UI/UX layer |
| Governance/compliance | Program office requires stage-gated budget approval | Favours a PRINCE2/PMBOK wrapper for governance |
| Team experience | Team has delivered Agile projects before; no PRINCE2 experience but PM office will run governance | Low risk either way |
| Organisational context | Sits under a wider program that reports via stage gates | Reinforces the governance wrapper |

### Recommendation
A hybrid: PRINCE2-style stage gates and a live business case for
program-level governance and budget approval, wrapping Agile/Scrum
sprints for the actual UI/UX delivery work. This isn't a compromise —
it matches both the governance requirement (fixed) and the genuine
requirement uncertainty in the delivery detail (not fixed).

### Holds as long as
The program office's stage-gate requirement doesn't change, and the
UI/UX scope stays the primary source of requirement uncertainty — if a
major compliance requirement later fixes the UI/UX scope too, the case
for keeping Agile at the delivery layer weakens and a fuller Waterfall/
PRINCE2 approach could be reconsidered.
