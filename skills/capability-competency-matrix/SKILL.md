# Capability / Competency Matrix

## When to use this

The user manages or is designing a team structure and needs a shared,
concrete definition of what's expected at each seniority level — for
hiring, performance conversations, or development planning.

## When NOT to use this

- A single, one-off hiring decision with no need for an ongoing
  framework — a simple job description is enough.
- The framework would immediately go unused (see pitfalls) — worth
  confirming there's a real plan to use it before building it.

## Workflow

1. **List the disciplines/skill areas relevant to what this team
   actually does** — generic categories borrowed from elsewhere are
   less useful than ones specific to the real work (e.g. for a
   consulting team: client management, problem-solving/analysis, change
   management, project management, business development — adapt to the
   actual team).
2. **Define the seniority levels** relevant to this team (e.g.
   Consultant → Senior Consultant → Manager → Senior Manager → Director,
   or whatever titles/levels actually exist).
3. **For every discipline × level cell, write a real description of
   what "good" looks like at that level** — not just a 1-5 rating with
   no definition. "Has led a project applying this discipline and holds
   relevant accreditation" is usable in a real conversation; a bare
   number 4/5 is not.
4. **Distinguish level progression clearly** — what specifically changes
   between "foundational" and "strong" for a given discipline, so the
   matrix can actually answer "what does this person need to do to get
   to the next level."
5. **State explicitly how the framework will be used** (hiring bar,
   development conversations, promotion criteria) — a framework built
   and never referenced in an actual conversation has no value; note
   this so it doesn't become a shelf document.

## Output format

```
## Competency framework: [team/roles]

Legend: [level definitions, e.g. Basic / Foundational / Strong / Expert]

| Discipline | [Level 1] | [Level 2] | [Level 3] | [Level 4] |
|---|---|---|---|---|
| ... | [description] | [description] | [description] | [description] |

### How this gets used
[Hiring / development conversations / promotion criteria — specific,
not generic]
```

## Common pitfalls

- Rating cells with a number and no description, which is unusable in
  an actual coaching conversation.
- Disciplines too generic to help a manager give specific feedback.
- Building the framework and never actually referencing it in hiring or
  development conversations — the most common way this becomes wasted
  effort.
- Levels that don't clearly distinguish from each other, making
  progression criteria fuzzy.

## Quality checklist

- [ ] Disciplines are specific to what this team actually does
- [ ] Every cell has a real description, not just a rating
- [ ] Level-to-level progression is clear enough to guide a development
      conversation
- [ ] There's a stated, real use for the framework (not a shelf document)
